## Story

**As a** solicitante, responsável ou administrador,
**I want** telas para consultar e gerenciar salas e solicitações de reserva,
**so that** eu possa acompanhar a disponibilidade e executar as ações permitidas ao meu perfil sem depender de um backend nesta entrega.

## Acceptance Criteria

1. **Given** a aplicação aberta no navegador, **when** o usuário seleciona um perfil, **then** a interface apresenta as telas de Solicitante, Responsável e Administrador sem exigir autenticação ou chamadas a backend.
2. **Given** a tela de Solicitante, **when** a lista de salas é exibida, **then** cada sala apresenta seu estado usando exatamente `DISPONIVEL`, `RESERVADA` ou `EM_MANUTENCAO`, com indicação visual distinta; salas reservadas ou em manutenção não oferecem ação de reserva.
3. **Given** uma sala `DISPONIVEL`, **when** o Solicitante informa início e término válidos e solicita a reserva, **then** a interface registra uma solicitação demonstrativa com estado `SOLICITADA` e atualiza a disponibilidade exibida durante a sessão.
4. **Given** uma reserva demonstrativa do Solicitante, **when** ele altera sua data/horário ou cancela a solicitação, **then** a interface atualiza a reserva ou a marca como `CANCELADA`, disponibilizando a sala novamente quando aplicável; início e término inválidos não são aceitos.
5. **Given** a tela de Responsável, **when** existem solicitações `SOLICITADA`, **then** o Responsável pode aprovar ou rejeitar cada solicitação, e a interface atualiza seu estado para `APROVADA` ou `REJEITADA`.
6. **Given** a tela de Administrador, **when** ele edita os dados demonstrativos de uma sala ou seleciona outro estado, **then** as alterações são refletidas nas telas e o estado pode ser apenas `DISPONIVEL`, `RESERVADA` ou `EM_MANUTENCAO`.
7. **Given** uma sala em `EM_MANUTENCAO`, **when** o Solicitante consulta ou tenta reservar a sala, **then** a sala aparece indisponível e não pode receber uma nova solicitação. Esse estado representa o bloqueio de novas solicitações para a sala; não é criado um novo status de reserva.
8. **Given** qualquer perfil e tamanho de tela, **when** as telas são utilizadas, **then** o layout permanece responsivo, as ações são compreensíveis e validações/indisponibilidades apresentam mensagens claras.
9. **Given** qualquer ação no protótipo, **when** a interface muda dados, **then** a alteração ocorre somente no navegador usando dados demonstrativos em memória; nenhuma API ou backend é requerido ou modificado.

## Dev Notes

- A entrega é somente frontend. As ações devem funcionar sobre dados demonstrativos no navegador e não podem introduzir endpoints, serviços ou alterações em entidades Java.
- O padrão Spring Boot para conteúdo estático é `src/main/resources/static/`. O repositório atualmente contém entidades Java em `src/main/java/.../projeto/`, mas não contém arquivos de frontend, `pom.xml`, configuração de build frontend ou testes automatizados detectáveis.
- `StatusSala` possui exatamente `DISPONIVEL`, `RESERVADA` e `EM_MANUTENCAO`. O último estado indica que novas reservas estão indisponíveis. [Source: `src/main/java/br/com/projeto_qualidade_software/projeto/enums/StatusSala.java`]
- `StatusReserva` possui `SOLICITADA`, `APROVADA`, `EM_USO`, `CONCLUIDA`, `REJEITADA`, `CANCELADA` e `NAO_COMPARECEU`. Aprovação e rejeição se aplicam a reservas `SOLICITADA`. [Source: `src/main/java/br/com/projeto_qualidade_software/projeto/enums/StatusReserva.java`; `src/main/java/br/com/projeto_qualidade_software/projeto/entities/Reserva.java`]
- A entidade `Sala` contém identificador, capacidade e estado. Não há nome ou localização definidos pelo modelo. Evitar sugerir que campos adicionais são persistidos; identificadores amigáveis apresentados no protótipo são apenas dados demonstrativos. [Source: `src/main/java/br/com/projeto_qualidade_software/projeto/entities/Sala.java`]
- A identidade visual solicitada é SENAC: azul, laranja e branco. Usar cores como apresentação visual; não há tokens oficiais de marca registrados no repositório.
- Requisitos relacionados: RF06, RF07, RF10, RF11 e RF17; RN01, RN04 e RN05. [Source: `docs/prd/requisitos-funcionais.md#3-reservas-e-alocacao`; `docs/prd/requisitos-nao-funcionais.md#evidencias-e-ferramentas-exigidas-pela-disciplina`]
- Não foram encontrados documentos de arquitetura, coding standards, tech stack, source tree ou estratégia de testes configurados em `core-config.yaml`. O código frontend deve seguir os padrões já existentes do Spring Boot e manter validações compatíveis com as ferramentas disponíveis, sem introduzir dependências de build não solicitadas.
- Não há epic local ou integração ClickUp disponível neste repositório; esta é a primeira story local (1.1), criada a partir do escopo solicitado e do PRD existente.
